Passkey RP ID / Public Suffix Test

Calls navigator.credentials.create() and .get() with RP IDs that a conforming WebAuthn implementation must refuse, such as public suffixes (github.io, netlify.app, co.uk) and unrelated domains. Use it with your password-manager extension active to see whether the extension enforces the same RP ID rules as the browser.

This page is not in a secure context. WebAuthn needs HTTPS (or localhost). Open it from its https:// URL.

Environment

How to read results

  • Expected: reject. A SecurityError (or TypeError) is a PASS. If a credential or assertion is returned, that is a FAIL: the extension (or browser) accepted an RP ID it should not have.
  • NotAllowedError is inconclusive. It means a prompt was cancelled or timed out. Watch whether the extension showed a "save passkey for …" UI for the disallowed RP ID, and retry.
  • For each issued credential the page also checks that rpIdHash in authenticatorData equals SHA-256 of the requested RP ID and that clientDataJSON.origin equals this page's origin.
  • The host profile decides which RP IDs are valid here and which sections apply. Every log entry is tagged with the profile, provider and user agent, so logs from GitHub and Netlify runs can be compared.
  • Browsers may require a click for each call, so if "Run all" stops with NotAllowedError, click the rows individually.

Partner origin and Related Origin Requests (RoR)

On a shared suffix host such as github.io or netlify.app the only RP ID this page can use is its own host. Related Origin Requests are the one legitimate way to use another RP ID: the page asks for an RP ID that belongs to a partner domain, and the browser accepts it only if the partner publishes /.well-known/webauthn listing this page's origin. The file lives on the partner, not on this page. An extension must perform the same check and must not issue credentials for an RP ID whose partner does not list this origin.

1. Partner origin

Your other deployment of this same page (GitHub ↔ Netlify). It is remembered in this browser.

2. Publish this file on the partner

The partner vouches for this page, so the file lists this page's origin. Serve it at: with no redirects and Content-Type: application/json.

Cross-RP credential tests (allowCredentials / excludeCredentials)

  
A credential ID belongs to exactly one RP. An authenticator must ignore IDs bound to another RP, and it must validate the
     RP ID before it looks at allowCredentials or excludeCredentials. An extension that matches by
     credential ID alone would use a passkey for the wrong RP, or reveal that a passkey exists for another site
     (InvalidStateError where none is expected). The passkeys these tests need are created automatically when you run them:
     RP A is this host, and RP B comes from the source below. They are remembered in this browser, so reloading does not create duplicates.

Iframe tests

  
Checks that the extension respects the same boundaries as the browser inside frames. A sandboxed frame has an opaque origin and
     must not get any RP ID. A cross-origin frame needs delegation through the allow attribute (Permissions Policy), and its RP ID must be
     valid for the frame's own origin, not the embedding page's. Browsers need a click inside the frame, so each test opens a frame
     and you press the button shown in it. The URL below is filled in from the partner origin and can be edited.
     The test frames are already in the page (created by markup). Tick the box to create them with script instead. A Chromium extension that injects a
     manifest content script with all_frames reaches both, so a difference between the two points to an injection problem.
     Same-origin and sandboxed tests load this page by URL; srcdoc frames are separate rows because they need extra manifest keys.
     Probe extension injection loads every frame type and reports whether credentials.create/get were replaced there,
     without needing a click.
